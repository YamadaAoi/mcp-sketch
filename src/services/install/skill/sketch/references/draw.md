## Hard Rules

1. **Never extract or decompress any archive, in any way**

2. **Prefer existing capabilities**: reuse the project's UI library and shared components; never reimplement equivalents — when basic interactive components (inputs / modals / tables, etc.) are needed but no UI library is installed, recommend stack-appropriate candidates for the user to choose, and **install only after confirmation**

## Drawing Workflow

1. The user asks to draw artboard X of design export Y. Check whether `list.json` for that design exists under the `.sketch-cache` folder

- No: run the `/sketch overview` command to overview the design
- Yes: continue
- If the design file's modification time is newer than list.json, or list.json clearly doesn't match what the user described, re-run `/sketch overview` to refresh it

2. Read artboard info: read `.sketch-cache/{design_file_name}/list.json` (generated by `/sketch overview`, `design_file_name = basename(file_path, '.zip')`), and get the artboard's preview image path and layer data size from the `artboards` array

- An artboard flagged `sliceBoard: true` is only **suspected** to be a slice-collection board — the flag is a heuristic (the slice share is an outlier across the design; real slice boards often sit far below any absolute threshold because designers annotate them with text layers). Confirm from the preview: a grid of assets with no page layout confirms it — not a page to reproduce, skip it (when drawing lacks a slice, follow the stage-3 slice lookup ladder); if the preview is ambiguous, ask the user
- **Read the artboard preview before fetching any data**: read only the preview of the artboard you are about to draw — vision gives what the data cannot: semantics (what each icon actually is) and functional-partition intuition; layer data read without the preview is hard to interpret, so split the page into components based on the preview. For the project's overall makeup and module division, the artboard names in the `artboards` array are enough — don't read every preview when the design has many artboards
- The `tokens` field is the aggregated design system (colors / font sizes / font families / radii / shadows / style names sorted by usage frequency); use it when building theme variables or checking design conventions — optional
- If the artboard's `size` is small (a simple artboard like a login page), read the whole artboard in one analyze call and skip the progressive stages below — the extra round trips aren't worth it for so little data

3. Fetch layer data progressively — **only fetch data for the component you are about to write, never for components not yet written** (every analyze response lands in your context; data for unwritten components only bloats it). Call `sketch_analyze` (MCP tool) or `npx -y mcp-sketch analyze` (CLI)

**Stage 1 — skeleton**: top-weighted layers form the layout skeleton (sidebar / card areas / table panels) and provide the coordinates for later region reads

```bash
npx -y mcp-sketch analyze -f "{file_path}" -p "{page_name}" -a "{artboard_name}" -l 20
```

Ranking is area-weighted: large layout containers first, detail layers last — a skeleton view, not an importance ranking

**Stage 2 — component planning**: decompose the page into components, as a senior frontend developer would, using the preview and the stage-1 skeleton

- Granularity: how many components this page deserves — regions with clear visual boundaries and self-contained function each become one component; over-splitting (one component per line of copy) and under-splitting (the whole page as one component) are both anti-patterns
- For each component settle: its responsibility boundary, the props and events it exposes, dependencies between components (who contains whom, who consumes whose data), and reuse potential (page-specific or a generic candidate; reuse what the project's UI library / shared components already cover — see the Hard Rules)
- Plan placement and routing here too: which file each component lands in, and how the page route is inserted (if needed)
- Once planned, summarize the plan for the user to review: the component list, each component's responsibility / props / events / dependency notes, reuse notes — adjust while it is cheap, before code reveals a wrong decomposition

**Stage 3 — region deep-read**: fetch a region's data only when you are about to write it; take the rect from the component boundaries planned in stage 2

- A region response covers every layer type inside it — text / shape / slice rows all included: slice rows carry the exported webp path (ready to import), and copy arrives with the region too. Full inventories are not pre-fetched; pull `-t "slice"` / `-t "text"` separately only for a unified asset tally (e.g. an icon map) or i18n / copy proofreading
- About to simulate a visual element with CSS or a hand-drawn SVG? That means this artboard carries no slice for that region — walk the **slice lookup ladder** first; only simulate when it turns up nothing:
  1. The design has suspected slice boards (flagged `sliceBoard: true` in list.json) → check there first: analyze the board — `-t "slice"` lists every slice with its name and webp path, `-n "{keyword}"` narrows by likely name; match against that board's preview, then import the matched rows' `assets` paths
  2. Not in the slice board either → look in similar regions of functionally similar artboards: reusable components (a menu bar, say) are usually sliced in only one artboard — browse other artboards' previews, find the one where that region is drawn most completely, and analyze that region there for the slices
  3. Nothing anywhere → reproduce with CSS or SVG as the last resort
- **Rect semantics**: `layers` holds layers fully inside the rect; slight straddles — layers inside the rect expanded by ~10px but not inside the rect itself — come back separately in the `adjacent` field (export jitter or a few px of overflow; judge whether each belongs to your component by its rect). Page-level containers (e.g. the full-canvas background) are in neither — they show up in the stage-1 skeleton
- `-e` marks regions already done, `-n` locates a specific element by name (details in the parameter table below)
- Deep-read every region once with analyze; do not reconstruct a region from the preview plus skeleton geometry alone
- For simple regions (plain stat panels) or unclear boundaries, continue paging the weight ranking with `-l`/`-o` instead of rect reads

**Parameters**:

| Arg  | Description                                                                                              |
| ---- | -------------------------------------------------------------------------------------------------------- |
| `-f` | **Required**. Design export path (zip or folder)                                                         |
| `-p` | **Required**. Page name                                                                                  |
| `-a` | **Required**. Artboard name                                                                              |
| `-r` | **Optional**. Component region `[x, y, width, height]`; result semantics see "Rect semantics" in stage 3 |
| `-e` | **Optional**. Regions already done, `[[x1,y1,w1,h1], ...]`; only layers fully inside are dropped         |
| `-n` | **Optional**. Filter by layer-name keyword (case-insensitive substring), e.g. logo, close button         |
| `-t` | **Optional**. Filter by type: `text` / `shape` / `slice`                                                 |
| `-l` | **Optional**. Layers to return; simple artboards 10~15, complex ones 20~30                               |
| `-o` | **Optional**. Return starting from the m-th layer (default 0)                                            |

**Response** (layer data is positional: the column order is declared once by `columns`, each row is read by position):

```json
{
  "pageName": "page name",
  "name": "artboard name",
  "width": 100,
  "height": 200,
  "total": 42,
  "previewPath": "preview image path (relative to project root)",
  "columns": [
    "index",
    "name",
    "type",
    "x",
    "y",
    "w",
    "h",
    "content",
    "css",
    "assets"
  ],
  "layers": [
    [
      0,
      "layer name",
      "text",
      10,
      20,
      100,
      30,
      "text content",
      ["font-size: 14px"],
      []
    ],
    [1, "layer name", "slice", 0, 0, 24, 24, "", [], ["asset path"]]
  ],
  "adjacent": [[2, "layer name", "text", 8, 20, 104, 30, "", [], []]]
}
```

- Each row in `layers` has 10 slots in the same order as `columns`: `index` (z-order), `name`, `type`, `x`/`y`/`w`/`h` (i.e. rect), `content`, `css`, `assets`
- Empty values are typed per column: `content` is `""`, `css`/`assets` are `[]`; slots are never omitted
- `layers` is sorted by layout weight descending (base score is area, layers with aspect ratio ≥ 30 get extra weight), and layers without visual properties are already filtered out
- `total` is the row count after filtering and duplicate-collapse (before pagination); use it with `-l`/`-o` to tell whether all pages have been read
- `index` is the original layer order (z-order, higher means closer to the top); use it to reason about occlusion between layers
- For `type: "text"` layers, slot 8 is the text content (`content`); styles (font / size / color / line-height, etc.) are in the `css` array
- The occasional `extras` field is keyed by `index` and carries that layer's `opacity` / `rotation` (only non-default values); the designer-named shared styles are aggregated in `tokens.styleNames` of list.json
- `adjacent` is returned only by rect queries (semantics see "Rect semantics" in stage 3); its rows use the same `columns`, are not counted in `total`, and are not affected by `-l`/`-o`
- `clones` carries duplicate collapse: when 3+ layers are identical except position and copy (table cells, list rows), one host row stays in `layers` and its copies become `[index, x, y]` tuples (`content` appended when non-empty) keyed by the host's `index` — style/name repeat once while every position, z-order and text survives; the host counts as one row in `total`. Set `LAYER_DEDUP=off` in `.env.sketch` to disable
- The `css` array carries the layer's main visual styles: font / size / color / line-height for text; background / gradient / radius / border / shadow for shapes; uninformative default declarations (`letter-spacing: 0`, etc.) are already filtered out
- `type: "slice"` layers contain exported assets; the `assets` array holds asset file paths (relative to the project root, already compressed to webp, ready for import); asset file names are pinyin-transliterated and usually meaningless — remap them to semantic names in code, and trace an asset's original export file name / layer / page / artboard in the `names` section of `.sketch-cache/assets-index.json`

4. Self-review: before the screenshot compare, check for reinvented basics that bypass the project's existing capabilities

- Basic interactive components — inputs, selects, date pickers, switches, modals, toasts, tables, pagination, etc. — are covered by any common UI library; hand-rolled implementations (native input/select, home-made modals) must be replaced with the library's equivalents, checked against the component-library inventory init summarized into the memory file; when the project has no UI library installed, follow the Hard-Rules recommendation flow and install only with the user's confirmation
- The project's own shared components take precedence the same way
- This pass only catches "should have used the existing one" basics; whether the visual reproduction is faithful is not judged here — that is the next step's quantified screenshot compare

5. If a `.env.sketch` config file exists in the project root with `SERVER_COMMAND` and `PREVIEW_URL` configured, call `sketch_dev` (MCP tool) or run the command below to start the dev server

```bash
npx -y mcp-sketch dev
```

6. If the local dev server started successfully, open the page with playwright-cli, explore what was drawn, take a screenshot, then call `sketch_compare` (MCP tool) or the command below to diff it against the base image; refine the page based on the similarity score and the diff image. The playwright-cli commands this project needs are summarized in `./references/browser.md`

- If screenshotting is available, save screenshots to `.sketch-cache/{design_file_name}/{page_name}/{artboard_name}/screenshot/{timestamp}.png`
- The screenshot must cover the whole rendered page: the design lays out below-the-fold content directly, while the real page may need scrolling to show it — capture a full-page screenshot (or set the viewport to the artboard size), and scroll through once first if content lazy-loads; a viewport-only screenshot silently skips below-fold content and over-reports the score

```bash
npx -y mcp-sketch compare -b "{preview_image_path}" -s "{screenshot_path}"
```

`compare` is a pure two-image differ with no knowledge of the design file: the screenshot is scaled to the base image's width, then diffed pixel-wise. Each side is localized upstream — `-b` is the base image (design side), `-s` is the implementation screenshot (page side). For a whole-page compare, `-b` is the artboard's `previewPath` from step 2 and `-s` is the full-page screenshot above

Returns `{ score, similarity, diffPath }`: the closer `score` is to 1, the better the match; `diffPath` is the amplified diff image (differences highlighted) for locating mismatched regions

Focused re-check of a single component (e.g. during the refinement loop below): run a region `analyze` on that component's rect and use the returned `previewPath` — an already-cropped region preview — as `-b`; take the matching element screenshot (playwright-cli `screenshot "{component wrapper selector}"`; the selector must be unique in the page, pass the output path via `--filename`) as `-s`. Both sides are already localized to the component, so the score is not diluted by surrounding content

**Refinement loop** (repeat until the part you drew matches the design):

- Locate mismatched regions via `diffPath`, then judge each difference against the screenshot and the artboard preview:
  - Real defects (missing or wrong layout / styles / copy / assets in the part you drew): fix them, then re-screenshot and re-compare; a missing image with no matching slice in this artboard goes through the stage-3 slice lookup ladder (suspected slice board → similar region in similar artboards → CSS/SVG)
  - Not defects: e.g. adding a component to a legacy page — your component matches the design, while the surrounding legacy page content differs from the artboard. Do not modify legacy code merely to raise the score; record these differences instead
- When finished, report the final score and output the recorded not-a-defect list to the user for confirmation

## Handling Edge Cases

### 1. The artboard name provided by the user doesn't exist in the design, or similar names exist

Consult `.sketch-cache/{design_file_name}/list.json` (run `/sketch overview` first if it doesn't exist) and offer the most likely artboard options for the user to confirm

### 2. No layer data can be read for some region of an artboard

Three possibilities:

- Shared functional regions (page header, nav bar, content area, etc.) are usually drawn in detail in only one artboard, with other artboards reusing those layers — look for the same functional region in other artboards' previews, and read the layer data there
- Some designers keep slice-type layers in a separate slice artboard — candidates are the artboards flagged `sliceBoard: true` in list.json (suspected flags; verify from their previews); locate one and read the data from the corresponding region there
- The designer did not draw that region — restore its layout from the preview image
