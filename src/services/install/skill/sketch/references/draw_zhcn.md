## 铁律

1. **禁止以任何方式解压任何压缩包**

2. **优先复用现有能力**：项目已有的 UI 库与通用组件直接复用，不重复实现同类能力；需要基础交互组件（输入框/弹窗/表格等）而项目未装 UI 库时，按技术栈推荐候选供用户选择，**确认后再安装**

## 绘制流程

1. 用户要求绘制 xx设计稿 里的 xx画板，判断`.sketch-cache`文件夹内是否存在 xx设计稿 的`list.json`

- 无：调用`/sketch overview`指令，概览 xx设计稿
- 有：继续
- 若设计稿文件的修改时间晚于 list.json，或 list.json 内容与用户描述明显不符，重新调用 `/sketch overview` 刷新

2. 读取 xx画板 信息：读取 `.sketch-cache/{design_file_name}/list.json`（由 `/sketch overview` 生成，`design_file_name = basename(file_path, '.zip')`），`artboards` 数组内获取 xx画板 的预览图路径与图层数据量

- 标记了 `sliceBoard: true` 的画板只是**疑似**切图收集板——启发式标记（切图占比在全部画板中断档领先；真实切图板常因设计师加的文字标注而远低于任何绝对阈值）。看预览图确认：资产网格、无页面布局即坐实——不是待还原的页面，跳过不画（需要切图时对它 analyze 取 slice 路径即可）；预览拿不准时询问用户
- **先看预览图，再取数据**：预览图只看当前要绘制的 xx画板——视觉能给你数据给不了的东西，语义（每个图标究竟是什么）与功能分区直觉；没有预览图对照，图层数据很难读懂，结合预览图划分页面组件。项目整体构成与模块划分看 `artboards` 数组里的画板名称即可，画板多时不必逐个读预览图
- `tokens` 字段为设计系统聚合（颜色/字号/字体/圆角/阴影/样式名按使用频次排序），建立主题变量或判断设计规范时使用，不强制
- 如果 xx画板 的 `size` 很小（如登录页这类简单画板），直接一次 analyze 读全画板，跳过下面的渐进阶段——数据量本来就小，没必要分次取

3. 渐进式获取图层数据——**只为即将编写的组件取数，不为还没写的组件取数**（analyze 的返回会进入上下文，用不上的数据只会撑大上下文）。调用 `sketch_analyze`（MCP 工具）或 `npx -y mcp-sketch analyze`（CLI）

**阶段 1 —— 骨架**：权重最高的图层构成布局骨架（侧边栏/卡片区/表格面板），并为后续区域精读提供坐标

```bash
npx -y mcp-sketch analyze -f "{file_path}" -p "{page_name}" -a "{artboard_name}" -l 20
```

排序按面积加权：大面积布局容器在前、细节图层在后——这是骨架视图，不是重要性排序

**阶段 2 —— 组件规划**：以资深前端的视角，结合预览图与阶段 1 骨架做组件拆解

- 拆解粒度：页面拆成多少个组件合适——视觉边界清晰、功能自成一体的区域各成一个组件；拆太碎（一行文案一个组件）与拆太粗（整页一个组件）都是反模式
- 每个组件明确：职责边界、对外的参数与事件、组件间依赖关系（谁包含谁、谁消费谁的数据）、复用情况（本页专用还是通用候选；项目 UI 库/通用组件已覆盖的直接复用，见铁律）
- 落点与路由一并规划：每个组件写到哪个文件、页面路由如何插入（如果需要）
- 规划完成后概括输出给用户过目：组件清单、各组件职责/参数/事件/依赖要点、复用情况——用户有异议此时调整，避免写完代码才发现拆解方向错了

**阶段 3 —— 区域精读**：即将编写哪个区域，才读取哪个区域的数据；rect 取自阶段 2 规划的组件边界

- 区域返回覆盖该区域内的全部图层类型——文本/形状/切图行都在内：切图行携带已导出的 webp 路径（可直接 import），文案同随区域返回。全量清单不预取，仅在需要统一清点切图（如建立图标映射）或 i18n/校对文案时，才用 `-t "slice"` / `-t "text"` 单独拉取
- **rect 语义**：`layers` 收完全落于 rect 内的图层；轻微压线——落于 rect 外扩约 10px 内、又不完全落于 rect 内的图层——单独收入 `adjacent` 字段返回（导出坐标抖动或元素溢出几像素的常见情形，按图层自身 rect 判断归属）。页面级容器（如全画布背景）两者都不含——阶段 1 骨架查询可见
- `-e` 标记已完成的区域，`-n` 按名字定位特定元素（详见下方参数表）
- 每个区域都要用 analyze 精读一次；不要跳过 analyze，仅凭预览图与骨架几何推断区域实现
- 简单区域（纯色统计面板等）或区域边界不清晰时，改用 `-l`/`-o` 按权重继续翻页，代替 rect 精读

**参数说明**：

| 参数 | 说明                                                                                          |
| ---- | --------------------------------------------------------------------------------------------- |
| `-f` | **必传**。xx设计稿路径（zip 或目录）                                                          |
| `-p` | **必传**。页面名称                                                                            |
| `-a` | **必传**。画板名称                                                                            |
| `-r` | **可选**。组件的矩形区域 `[x, y, width, height]`；返回语义见上方「rect 语义」                 |
| `-e` | **可选**。排除的矩形区域列表 `[[x1,y1,w1,h1]]`；只有完全落于排除区域内的图层才被丢弃          |
| `-n` | **可选**。按图层名关键词过滤（大小写不敏感的子串匹配），快速定位特定图层（如 logo、关闭按钮） |
| `-t` | **可选**。按图层类型过滤：`text` / `shape` / `slice`                                          |
| `-l` | **可选**。返回的图层数量；简单画板 10~15 个，复杂画板 20~30 个                                |
| `-o` | **可选**。从第 m 个图层开始返回（默认 0）                                                     |

**返回结构**（图层数据为定位数组：列序由 `columns` 声明一次，每行按序取值）：

```json
{
  "pageName": "页面名称",
  "name": "画板名称",
  "width": 100,
  "height": 200,
  "total": 42,
  "previewPath": "预览图路径（相对项目根目录）",
  "columns": [
    "index",
    "name",
    "type",
    "x",
    "y",
    "w",
    "h",
    "content",
    "css",
    "assets"
  ],
  "layers": [
    [0, "图层名", "text", 10, 20, 100, 30, "文本内容", ["font-size: 14px"], []],
    [1, "图层名", "slice", 0, 0, 24, 24, "", [], ["切图路径"]]
  ],
  "adjacent": [[2, "图层名", "text", 8, 20, 104, 30, "", [], []]]
}
```

- `layers` 每行 10 个槽位、顺序与 `columns` 一致：`index`（z-order）、`name`、`type`、`x`/`y`/`w`/`h`（即 rect）、`content`、`css`、`assets`
- 空值按列类型固定：`content` 为 `""`，`css`/`assets` 为 `[]`，槽位永不省略
- `layers` 已按布局权重从高到低排序（基础分为面积，长宽比≥30的图层额外加权），且已过滤掉不含视觉属性的图层
- `total` 为过滤并折叠重复后的行数（分页前），配合 `-l`/`-o` 判断是否翻完
- `index` 为原始图层顺序（z-order，值越大层级越高），用于判断图层的遮挡关系
- `type: "text"` 的图层第 8 列为文本内容（`content`），样式（字体/字号/颜色/行高等）见 `css` 数组
- 偶现字段 `extras` 以 `index` 为 key，携带该图层的 `opacity`/`rotation`（仅非默认值时出现）；设计师命名的共享样式聚合见 list.json 的 `tokens.styleNames`
- `adjacent` 仅在区域查询时返回（语义见上方「rect 语义」）；行格式与 `columns` 一致，不计入 `total`，不受 `-l`/`-o` 分页影响
- `clones` 承载重复折叠：成员数 ≥3、除位置与文案外完全相同的图层（表格单元格/列表项等）只保留一行宿主在 `layers`，其余折叠为按宿主 `index` 索引的 `[index, x, y]` 元组（文案非空时附加在第 4 位）——名称/样式只重复一次，位置/层级/文案全部保留；宿主在 `total` 中计一行。`.env.sketch` 配 `LAYER_DEDUP=off` 可关闭
- `css` 数组承载了图层的主要视觉样式：文本的字体/字号/颜色/行高，形状的背景/渐变/圆角/边框/阴影；无信息量的默认值声明（`letter-spacing: 0` 等）已过滤
- `type: "slice"` 的图层是包含切图的图层，`assets` 数组为切图文件路径数组（相对项目根目录，已压缩为 webp，可直接用于 import）；切图文件名经拼音转写、通常无语义——在代码里重映射为语义名再用，原始导出文件名/图层/页面/画板可按 `.sketch-cache/assets-index.json` 的 `names` 段溯源

4. 自查：截图比对前，检查有没有绕过项目现有能力重复造轮子

- 基础交互组件——输入框、下拉选择、日期选择、开关、弹窗、消息提示、表格、分页等——通用 UI 库一般都有；手写实现（原生 input/select、自制弹窗等）一律替换为 UI 库等价组件，对照 init 汇总到记忆文件的组件库信息；项目尚未安装 UI 库时，按铁律的推荐流程征得用户确认安装
- 项目内已有的通用组件同理优先复用
- 只查这类"该用没用"的基础问题；视觉还原是否到位不做主观判断，交给下一步截图比对量化

5. 如果项目根目录存在配置文件`.env.sketch`，且配置了`SERVER_COMMAND`和`PREVIEW_URL`，调用 `sketch_dev`（MCP 工具）或执行以下命令启动开发服务

```bash
npx -y mcp-sketch dev
```

6. 如果本地服务启动成功，用 playwright-cli 打开页面、探索本次绘制的内容，截图后调用 `sketch_compare`（MCP 工具）或以下命令与基准图对比，根据相似度分数与差异图修正页面；本项目用到的 playwright-cli 命令速查见 `./references/browser.md`

- 如果截图功能可用，把图片保存到`.sketch-cache/{design_file_name}/{page_name}/{artboard_name}/screenshot/{timestamp}.png`
- 截图必须覆盖整个渲染页面：设计稿把滚动线以下的内容直接铺开呈现，实际页面可能要滚动才出现——用整页截图（或把视口调成画板尺寸）再截，内容懒加载时先滚动一遍触发加载；只截视口会静默跳过滚动线以下的内容，分数虚高

```bash
npx -y mcp-sketch compare -b "{preview_image_path}" -s "{screenshot_path}"
```

`compare` 是纯两图差异器，不感知设计稿：截图按基准图宽度缩放后逐像素比对。两侧各自在上游完成定位——`-b` 为基准图（设计侧），`-s` 为实现截图（页面侧）。整页比对时 `-b` 取第 2 步画板的 `previewPath`，`-s` 用上面的整页截图

返回 `{ score, similarity, diffPath }`：`score` 越接近 1 越一致；`diffPath` 为差异放大图（差异处高亮），用于定位还原不一致的区域

单个组件的聚焦复查（如下方修正循环中）：对该组件的 rect 做一次区域 `analyze`，用返回的 `previewPath`——已按 rect 裁剪的区域预览图——作为 `-b`；用对应的元素截图（playwright-cli `screenshot "{组件包裹节点选择器}"`，选择器须在页面内唯一，输出路径用 `--filename` 指定）作为 `-s`。两侧都已定位到组件本身，分数不被周围内容稀释

**修正循环**（可多轮，直到本次绘制的部分与设计稿一致）：

- 结合 `diffPath` 定位不一致区域，对照截图与画板预览逐块判断差异性质：
  - 确实是问题（本次绘制部分的布局/样式/文案/切图缺失或错误）：修复后重新截图、重新对比
  - 不算问题：例如在存量页面上加组件——组件部分与设计稿完全一致，存量页面部分本来就和画板不同。不要为了提升分数去改动存量代码，记录这些差异
- 修正完成后，向用户汇报最终分数，并把记录的"不算问题"差异清单输出给用户确认

## 意外情况处理

### 1、用户提供的画板名称在设计稿内不存在，或者有相似的画板名称

结合`.sketch-cache/{design_file_name}/list.json`（不存在时先调用 `/sketch overview`），提供最可能的一批画板选项供用户选择确认

### 2、某画板某块区域读取不到图层数据

有三种可能性：

- 不同画板的相同功能区（页面头部、导航栏、内容区域等）通常只在其中一个画板详细绘制，其余画板参照复用——结合预览图在其他画板找到同一功能区后，从该区域读取数据
- 部分设计师习惯将切图类图层放在单独的切图画板——候选是 list.json 中标记 `sliceBoard: true` 的画板（疑似标记，看预览图核实），找到后对对应区域读取数据
- 设计师确实未绘制该区域——结合预览图尝试还原该区域的布局
